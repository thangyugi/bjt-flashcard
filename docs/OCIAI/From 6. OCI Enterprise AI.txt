Model Context Protocol

Hello, and welcome back. You saw that your agent could call functions you wrote. But real agents also need to reach tools and systems. MCP stands for Model Context Protocol. Launched in 2024, it's an open standard that alloww AI applications to connect to external tools, data sources, and systems in a consistent way. The important phrase here is open standard that is not tied to any one vendor.

It is built on JSON-RPC 2.0, which is a simple and widely used protocol for structured request response communication, and it is governed by Agentic AI Foundation. Think of MCP as a common language that both sides agree on-- the AI application and the tool.

You will often hear the analogy USB-C for AI. Just like USB-C lets any device connect to any compatible port, MCP lets any compatible client connect to any compatible server, and that's the core idea. A standardized connectivity.

Before MCP, every AI application had to build custom integrations with every tool. So if you had three AI apps and four tools, you need 12 separate integration. And that's the N into M problem. It grows very quickly and becomes hard to maintain.

MCP changes that. Now each AI app builds one MCP client, and each tool exposes one MCP server. Any MCP compatible client can talk to any MCP compatible server, regardless of who built them. So instead of 12 integrations, you now only need seven. That's the shift from quadratic complexity to linear complexity, and that's why MCP matters.

The MCP architecture has three key participants-- the host, the client, and the server. The host is the AI application the user interacts with like cloud desktop cursor IDE or VS code. Inside the host, an LLM or the AI model does the reasoning. The host creates one or more MCP clients. Each client maintains a dedicated one on one connection with one MCP server.

Again, MCP servers are the programs that provide context-- tools to execute, data to read or prompt templates. Each server can connect to external systems like GitHub, Slack, databases, or the local file system.

Remember that the client and server are decoupled. The server doesn't care which application is calling it. As long as the protocol is followed, any client can connect to any server. The host is responsible for managing context aggregation across clients.

One other thing you need to remember is that STDIO Standard Input/Output Transport Protocol is used for local servers. Streamable HTTP transport protocol is the standard for remote servers.

MCP servers expose three types of primitives. First, tools. These are the actions the model can take. Think of them like functions that actually do something. Second, resources. These are the data sources. The model reads them for context.

And third, prompts. These are templates that structure interactions. And these are user controlled. A simple way to remember this is tools means do something, resources means read something, and prompts means structure something. It is mainly a UI shortcut that activates a predefined prompt. System might inject a prompt command loads a prompt template.

Tools are the most commonly used primitives. Most of the time when people talk about MCP, they are mainly thinking about tools. Here is how MCP calling works on OCI.

Notice what didn't happen. Control never came back to your app to make the call. And that gives you three things. No client round trip since OCI reaches the server itself. Lower latency because there are fewer hops, and it runs over streamable HTTP, the supported transport protocol.

That direct path is the key contrast, which we saw earlier in the last lesson. In function calling, the model says what it wants. Control returns to your app.

But here's the thing to internalize first. By default, each model call is independent and remembers nothing. And this is because underlying LLMs don't retain any internal memory of past interactions.

There are two kinds of memory, and the difference is how long the context needs to live. Short-term memory works within a single conversation. It remembers the earlier turns in the same chat. It is managed with the Conversation API and previous response ID, and it lasts for the life of that conversation.

Long-term memory works across conversations. It remembers a user across separate chats, even days apart. It's durable and keyed to a subject ID within a project, and it persists beyond any single conversation.

Let's look at short-term memory concretely. Within one conversation, the turns linked together. Turn 1-- how many PTO days do I have? Agent replies you have 8 left. Turn 2 and next year still, the agent replies, you will accrue 20. It understood next year meant PTO because it saw turn 1.

But there is a cost to remembering. And compaction is how OCI manages it. Because every turn effectively resets the history, a long conversation keeps growing. More tokens, more latency, more cost with each turn. Compaction fixes this by condensing the chat history into retained memory, which is a compact summary of earlier turns.

The agent keeps the meaning of what was said without dragging the full transcript along every time, and this is what keeps a long conversation affordable and fast. Long-term memory is the durable kind, and the key is the subject ID.

Picture a user who says on Monday in one conversation, I prefer afternoon meetings and that gets saved. Then on Thursday, in a brand new conversation, user says schedule my one on one and the agent books it for 3:00 PM as the user preferred.

The agent remembered across two separate conversations. That works because the memory is durable and keyed to a subject ID within a project. The subject ID ties memories to one person so the agent can recall them in a completely new chat.

Introduction to Oracle AI Vector Search
In this lesson, we look at embeddings vectors and introduce Oracle AI Vector Search. Let's start with the core problem. Traditional database searches rely on exact keyword matching. If you search for "canine," you won't find documents that talk about dogs. This is frustrating for users. They care about meaning, not exact words.

Semantic search powered by vectors solves this. It converts text into mathematical representations that capture meaning. So "canine" and "dog" end up close together in vector space, and a similarity search finds them both. Oracle AI Vector Search brings this semantic search capability directly into the Oracle database, letting you combine it with regular SQL queries. Let's break down the core concept.

A vector is just a list of numbers. Think of it as GPS coordinates, but in hundreds or thousands of dimensions instead of just two. An embedding model is a neural network that converts data, text, images, audio into these vectors. The magic is that similar things get similar vectors. Imagine a map where every word, sentence, or document has a location. Similar things are plotted close together. Different things are far apart.

In our map analogy, "dog," "puppy," and "canine" all cluster together because they mean similar things. "Car" is far away because it's semantically different. Oracle can even run ONNX embedding models directly inside the database. Here's the pipeline for creating embeddings. First, your input data, whether it's text, images, or audio, enters the pipeline. A tokenizer breaks the text into tokens, which are word pieces. For example, BERT's tokenizer splits embedding use a case for chunking into eight tokens.

Then a neural network, typically a transformer model, processes these tokens and produces a vector. This vector captures the semantic meaning of the entire input, what we call as embedding. Important to know, tokenizers have limits on how many tokens they can process. Usually 5, 12, or so. That's why we need chunking for large documents, which we'll cover later.

Oracle AI Vector Search is not a separate product, it's built right into Oracle Database. This is a huge advantage. You don't need to set up and maintain a separate vector database like Pinecone. Your vectors live right next to your business data, like customer records, orders, products, all in one place.

And the best part, you use standard SQL. The VECTOR_DISTANCE function lets you find similar items. You get all of Oracle's enterprise features-- security, transactions, backup, and scalability. The VECTOR_DISTANCE function lets you find similar items, and you can combine it with regular WHERE clauses. For example, find houses that look like this photo where price is less than $500k and city is New York City all in one query.
Oracle AI Vector Search Workflow
In this lesson, we will cover Oracle AI vector search workflow. This is the full Oracle AI vector search workflow. Step 1, generate embeddings. You can do this inside the database using ONNX models or externally via REST APIs from OpenAI, Cohere, et cetera.

Step 2, store vectors in Oracle tables using the vector data type alongside your regular business data. Step 3, create vector indexes. Without indexes, similarity search scans every vector. That's fine for thousands, but painful for millions.

Oracle supports two types of vector indexes. Hierarchical Network Small World builds a multi-layered graph in memory. It's the fastest for queries. Inverted file flat partitions vectors into clusters using k-means. Then only searches the nearest partitions during a query.

Step 4, run similarity queries using VECTOR_DISTANCE combined with standard SQL predicates. Step 5, use the results for RAG, retrieval-augmented generation, by feeding relevant chunks to an LLM. Oracle provides chainable utility functions that let you do the entire pipeline in one SQL statement, convert PDF to text, chunk it, and generate embeddings.

There are two ways to generate embeddings. The in-database approach uses Oracle's built-in ONNX Runtime. You import an ONNX format model, like Hugging Face's all-MiniLM-L12-V2 directly into the database. Then use the VECTOR_EMBEDDING SQL function to generate embeddings entirely within the database. No network calls, no latency, no data leaving the database.

The external approach calls third-party REST APIs, like OpenAI or Cohere, via PL/SQL. This gives you access to the latest and most powerful embedding models. Oracle provides the DMBS_VECTOR_CHAIN package with chainable utility functions that make this seamless. You can even chain-text extraction, chunking, and embedding into a single pipeline.

Chunking is a critical step for large documents. Embedding models can only process a limited number of tokens at a time, typically around 512. So a 100-page PDF must be split into smaller, meaningful chunks first. Oracle provides chainable utility functions for this.

UTL_TO_TEXT converts PDFs and Word docs to plain text. UTL_TO_CHUNKS splits text into pieces. And UTL_TO_EMBEDDINGS generates vectors for each chunk.

The amazing thing about Oracle is you can chain all three together in a single SQL insert statement. That code on screen takes a PDF, converts it to text, chunks it, generates embeddings, and stores everything in one go. The chunking function supports different strategies-- by words, sentences, or paragraphs-- and you can customize parameters, like chunk size, and overlap.

Oracle's vector data type is flexible and powerful. At its simplest, you declare vector with no parameters, and it accepts any dimensions and format. Or you can be strict. Vector(768, INT8) enforces that every vector must have exactly 768 dimensions stored as 8-bit integers.

The four storage formats are FLOAT32, the default 4 bytes per dimension; FLOAT64, 8 bytes for extra precision; INT8, 1-byte, very compact; and binary, 1-bit per dimension, ultra compact. You can also choose between dense storage, every dimension stored, and SPARSE storage-- only non-zero dimensions stored, great for sparse embedding models.

Vectors are stored internally as secure file blobs. Most embedding vectors are between 1.5 KB and 12 KB. Similarity search works by measuring the distance between vectors. Oracle supports four distance metrics. COSINE is the most popular for text. It measures the angle between vectors and is the default if you don't specify one.

EUCLIDEAN L2 measures straight-line distance and is great for spatial data. DOT PRODUCT INNER PRODUCT considers both direction and magnitude. MANHATTAN L1 sums absolute differences and is robust to outliers.

The VECTOR_DISTANCE function takes two vectors and a metric, returning the distance. Smaller distance means more similar. You typically order by distance and fetch first N ROWS to get the top k most similar results. Important, always use the same distance metric that your embedding model was trained with. Most text models recommend COSINE_DISTANCE.
Oracle AI Database Private Agent Factory
In this lesson, we will learn about Select AI Agent framework. Select AI Agent is the autonomous agent framework that ships with Oracle AI Database. The key insight is the word "inside." Most agent frameworks today live in your application code-- LangChain or LangGraph or a Python script-- and they reach into your database from the outside.

Select AI agent flips that, the agent is a database citizen. It uses an LLM configured through an AI profile, accesses enterprise data through SQL and tools, and is managed through PL/SQL APIs, such as DBMS_CLOUD_AI_AGENT. There are four behaviors every agent exhibits.

Plan-- figure out the steps. Use tools-- RAG, NL2SQL, custom PL/SQL functions, or external REST calls. Reflect-- did that result actually answer the question? Remember-- keep context within a conversation and across conversations. Select AI capabilities span Oracle AI Database deployments, with many public examples currently documented through Autonomous AI Database.

Before we go deeper into the framework, it helps to ask why even put an agent inside the database. On the left is the standard pattern most teams use today. An external orchestrator written in Python or JavaScript talks to the database, exports rows, calls an LLM, and reasons in the application tier. That works, but it has costs, data movement, separate infrastructure, separate security model, and lots of glue code.

On the right, Select AI agent inverts this. The agent is defined in PL/SQL, lives in the same engine as your tables, and reuses everything Oracle AI Database already gives you-- role-based access, virtual private database, encryption, audit logs, and the connection pool.

The practical effect-- less data movement, fewer credentials to manage, and security policies that apply automatically, because agent operations can be governed through standard Oracle Database security and privilege models. Select AI Agent has four cooperating layers. They map roughly to the four steps of react, but with separation of concerns.

Planning is the strategy layer. It interprets the request, identifies missing details, and proposes an ordered sequence of actions. Tool use is the execution layer. For each action, it picks the right tool. There are three categories of tools, and we'll cover them on the next slide.

Reflection is the quality check layer. It compares what came back from the tool against what the agent expected. If results look wrong, if there was a tool error, or if a human disapproved an action, the agent revises its plan. Memory management is the context layer. Short-term memory keeps the current conversation coherent. Recent messages and intermediate tool results.

Long-term memory persists across sessions, recording user preferences, prior strategies, and history. These layers run for every single user turn. Tools are how agents do anything useful. Select AI Agent groups them into three categories.

The framework includes built-in capabilities such as RAG, SQL generation, notifications, and web search. RAG runs retrieval-augmented generation against a vector index that you've already set up. The agent searches your documents, finds relevant chunks, and uses them to ground its answer.

NL2SQL turns natural language questions into SQL queries that run against approved tables and views. Custom PL/SQL tools are where most production value lives. You probably already have hundreds of stored procedures that update orders, validate addresses, or run calculations.

You wrap one in a tool definition, and the agent can call it. Core orchestration stays close to enterprise data, while tools can securely reach external systems. External rest tools let the agent reach outside-- web search for fresh information, email and Slack for notifications, or any HTTP endpoint. You wrap the HTTP call in a small PL/SQL function and register it. The power comes from mixing them.

A single workflow might use NL2SQL to fetch order data, a custom PL/SQL function to update status, and an email tool to notify the customer, all in one agent run. Let's make this concrete. Oracle's docs include a worked example, a customer return agent that handles multi-turn product return conversations.

On the left is the trace of one interaction. The user asks to return an order. The agent plans the steps in its head-- find the order, check eligibility, update status, notify. It calls NL2SQL to fetch the order from the database. It looks at the result and confirms the order is within the return window.

Then it calls a custom PL/SQL tool-- Update_Order_Status_Tool-- to actually change the status to return approved. The reflection step confirms the update succeeded. Finally, it composes the user-facing reply.

On the right is the actual PL/SQL that creates the agent. The workflow begins with CREATE_AGENT, then associates tools, tasks, and agent teams. You give it a name pointed at an AI profile and write a one-sentence role. The role is the system prompt. It tells the LLM how to behave.

The point of this slide, a useful agent in production, is maybe 20, 30 lines of PL/SQL plus the tools it needs. It's much smaller than people expect.

Oracle Autonomous AI Database MCP Server
In this short lesson, we're going to look at a brand-new managed MCP server from Oracle, one that runs inside the database itself. This is not a third-party MCP server that you download and run next to your database. It is part of the Database Service.

When you turn it on, the database itself starts answering MCP requests. With this one, there is no separate process. Oracle handles deployment, patching, scaling, and high availability. Because it speaks plain MCP over HTTPS, any MCP-compatible client connects to it the same way. Any LangChain or OpenAI Agents SDK client we built in earlier modules can consume it.

MCP clients are anything that speaks the MCP protocol. The client talks to a single HTTPS endpoint. That is the entire transport surface. Streamable HTTP is the MCP transport mode that we discussed in the foundational MCP module.

Two things are happening inside the database. First, the MCP server endpoint in the teal-bordered inner box. This is the new piece. It is multi-tenant, meaning the same Oracle-managed service serves many ADB instances, and each instance gets its own URL keyed off its OCID. It is Oracle-managed. They handle uptime, patching, and scaling.

Second, Select AI Agent tools in the purple-bordered inner box. Select AI Agent is the existing framework you use to define database tools. The MCP server does not invent a new tool format. It simply exposes whatever Select AI Agent tools you have already defined. So if you create three tools today, those three tools instantly become callable MCP tools.

NL2SQL is the headline use case-- Natural Language to SQL using an AI profile, which is the trick that bypasses schema discovery. RAG lets the AI search over data you have indexed. Custom PL/SQL is the escape hatch. Anything you can write as a PL/SQL function, you can register as an MCP tool.

Endpoint consists of a few components. Region is your home region like a Chicago one. Database OCID uniquely identifies one Autonomous AI Database instance. If you have 10 ADB instances, you get 10 different MCP endpoints.

Finally, the authentication callout at the bottom. The AI client uses normal database credentials. Whatever the user is allowed to do in the database, that is exactly what the AI is allowed to do through the MCP server. RBAC, ACLs, and VPD all apply unchanged.
